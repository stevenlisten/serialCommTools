# 记录：T001-010 日志偶尔乱码 · 原因分析（实证）

- 时间：2026-08-02
- 现象：日志（接收区显示 / 导出 / 自动保存）偶尔出现乱码
- 方法：对 5 类候选成因逐一用注入式探针实证复现（tools/debug_mojibake.cjs）

## 成因清单（按可能性排序）

### 1. 编码不匹配（最常见，占绝大多数）
- 设备发送 **GBK/GB2312 中文**，工具默认按 **UTF-8** 解码
- 实证：GBK 字节 D6 D0 CE C4 按 UTF-8 解码 -> 显示 4 个替换符 `����`（U+FFFD）
- 特征：只有含中文的行乱，英文/数字行正常；表现为“偶尔”（仅当报文含中文时）
- 解决：把工具栏「编码」切换为 **GBK**

### 2. 二进制数据在文本模式下显示
- 串口流中混有二进制帧/校验字节（0x80-0xFF、控制符），文本模式把它们显示为替换符 `�`（fatal:false 设计）
- 实证：字节 01 02 80 FF FE -> 显示 `[ts] 01 02 �� �`（0xFFFD 替换）
- 解决：查看/记录二进制数据请用 **HEX 模式**

### 3. UTF-8 BOM 头
- 设备每条报文带 UTF-8 BOM（EF BB BF），首字符显示为不可见/怪异字符（U+FEFF）
- 实证：BOM+“中” -> 行首出现 U+FEFF（部分环境显示为 ），其后中文正常
- 解决（建议改进）：收到首字节 BOM 时剥离（当前版本未处理）

### 4. 跨重连/参数热更新的多字节字符截断（真实边界缺陷）
- 连接期间参数热更新会重开端口并**重建 TextDecoder**；若一个多字节字符（如“中”的 3 字节）恰被拆在重连前后，尾字节被新解码器单独解码 -> 偶发单个 `�`
- 实证：E4 B8 + 热更新 + AD -> 显示 U+FFFD
- 解决（建议改进）：同编码时复用解码器实例（保留流状态），编码变化时才重建

### 5. 日志文件本身是 UTF-8 无 BOM
- 导出/自动保存的 .log 为 **UTF-8 无 BOM**（实证：文件头 23 20 53...，无 EF BB BF）
- 用 GBK 默认的旧版记事本/部分中文文本工具打开 -> 中文显示乱码，**文件内容其实正确**
- 解决：用支持 UTF-8 的编辑器（VSCode/新版记事本/Notepad++）打开

## 结论
- 主要成因是**编码不匹配（GBK vs UTF-8）**，属于使用配置问题，不是程序缺陷
- 真实程序缺陷 1 个：跨重连多字节截断（成因 4，影响极小、偶发）
- 可改进 2 项：BOM 剥离（成因 3）、同编码复用解码器（成因 4）
